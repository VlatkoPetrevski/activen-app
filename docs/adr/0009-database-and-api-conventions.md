# ADR-0009: База на податоци и API конвенции

- Статус: Прифатено
- Датум: 2026-11-18

## Контекст

Инкремент 1 ја воведува PostgreSQL шемата (Garmin референтен модел, ADR-0007) и API скелетот.
Потребни се конзистентни правила за пристап до база, миграции, тестирање и грешки, пред да се
додадат идентитет (инкремент 2) и синхронизација со вендори (инкремент 4).

## Одлука

### 1. ORM и миграции

- **Drizzle ORM** (`packages/db`) — TypeScript-шема, SQL-блиску прашања, без runtime магија.
  Алтернативи: Prisma (посебен генератор и query engine, послаб SQL пристап), TypeORM (слаби типови).
- Миграциите ги генерира `drizzle-kit` од `src/schema.ts` и се **commit-ираат** (`packages/db/migrations`).
  CI проверува дека шемата и миграциите се усогласени (генерирањето не смее да произведе нова датотека).
- Миграциите се извршуваат со посебна команда (`pnpm --filter @activen/db db:migrate`), не при старт на API.

### 2. Конвенции на шемата

- Имиња на колони во `snake_case`; полињата за активности ги следат имињата и единиците на Garmin
  (`distance_in_meters`, `duration_in_seconds`, …).
- Примарни клучеви `uuid` (`gen_random_uuid()`); времиња `timestamptz`; календарски датуми `date`.
- Енуми во Postgres за стабилни множества (вендор, улога, статус); слободен `text` + проверка во domain за
  отворени множества (тип на активност).
- Ограничувања во базата, не само во кодот: unique (вендор + надворешен ID), check (RPE 1–10),
  делумен unique индекс (една активна врска тренер–спортист), забрана за самотренирање.
- Токените од вендори се чуваат шифрирани (`bytea`); шифрирањето е одговорност на апликацијата (инкремент 4).
- Сирови податоци од вендор (`raw jsonb`) се чуваат за повторна обработка без нов повик до вендорот.

### 3. Repository слој

- Секој агрегат има repository; API и worker не пишуваат SQL директно.
- **Идемпотентни upsert-и** (`ON CONFLICT … DO UPDATE`), со `xmax = 0` за разликување insert/update —
  повторено webhook известување не создава дупликат.
- **Оптимистичка конкуренција** за план: `version` колона + `expectedVersion`; конфликт → `ConflictError` (HTTP 409).
  Секоја промена запишува снимка во `plan_entry_versions` (историја за тренер и спортист).
- **Верзионирање на HR зони** со advisory lock по спортист — нема две верзии со ист датум на важење.
- **Sync настани**: прифаќање со `FOR UPDATE SKIP LOCKED`, статус `processing` + `claimed_at` (lease).
  Истечен lease се враќа во работа; по максимален број обиди → `failed`. Повеќе worker-и не преземаат ист настан.
- **Пристап на тренер** само преку `authorizeCoachRead`: проверка на активна врска + согласност по опсег
  (scope) и запис во `audit_log`.
- Сметки не се поврзуваат автоматски по е-пошта (заштита од преземање сметка) — поврзувањето е експлицитно.

### 4. Грешки и API

- Доменски грешки (`NotFoundError`, `ConflictError`, `ValidationError`) → **RFC 9457 problem+json**.
- URI верзионирање (`/v1/...`); health проби без верзија (`/health/live`, `/health/ready`).
- OpenAPI на `/docs` (`/docs/openapi.json`) — договор за web и мобилната апликација.
- Конфигурација само преку env, валидирана со zod при старт (грешка → процесот не стартува).
- Структурирани логови (pino) со `x-request-id` и редакција на чувствителни заглавја.

### 5. Тестирање

- Интеграциски тестови против **вистински PostgreSQL 16**: глобален setup создава привремена база
  (`activen_test_<random>`) на серверот од `TEST_DATABASE_URL`, ги извршува миграциите и ја брише на крај.
- Не користиме Testcontainers: истиот пристап работи локално (Docker Compose), во CI (service container) и во
  околини без Docker.
- Пред секој тест табелите се празнат (`TRUNCATE … CASCADE`); тестовите во пакет се извршуваат секвенцијално.

## Последици

- - Типизиран SQL, миграциите се ревидираат во git, идемпотентност и конкуренција гарантирани од базата.
- - Тестовите ги фаќаат вистинските грешки на SQL ниво (на пр. редослед `LIMIT` / `FOR UPDATE`).
- − Интеграциските тестови бараат Postgres (локално `docker compose up -d db`).
- − Drizzle е помлад од Prisma; ризикот е мал бидејќи шемата и миграциите се обичен SQL.
