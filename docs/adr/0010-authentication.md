# ADR-0010: Автентикација и сесии

- Статус: Прифатено
- Датум: 2026-11-18
- Ја затвора отворената точка од ADR-0004 (избор на библиотека/провајдер)

## Контекст

ADR-0004 одлучи: најава со Google, Apple и email (без лозинки), сопствена табела `users` и улоги.
Остана изборот: библиотека (Better Auth, Auth.js), управуван IdP (Auth0, Clerk, Zitadel) или сопствена тенка
имплементација врз стандарди.

## Опции

| Опција                                                | За                                                                          | Против                                                                                                               |
| ----------------------------------------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Управуван IdP (Auth0, Clerk)                          | Готов UI, MFA                                                               | Цена по корисник, податоци надвор од нашата ЕУ база, втор извор на вистина за корисници                              |
| Better Auth / Auth.js                                 | Многу провајдери                                                            | Сопствени табели и модел на корисник (судир со нашата шема), Next.js/Express ориентирани, послаба контрола над сесии |
| **Сопствена тенка имплементација врз OIDC стандарди** | Една шема, целосна контрола (сесии, улоги, согласности), лесна за тестирање | Ние сме одговорни за безбедноста → ограничен опсег + стандардни библиотеки (`jose`)                                  |

## Одлука

Сопствена тенка имплементација. Не пишуваме криптографија и не чуваме лозинки: верификација на
токени со `jose`, а Google/Apple ја прават автентикацијата.

### Текови на најава

1. **Google / Apple** — клиентот (web: Google Identity Services / Sign in with Apple JS; мобилно: native SDK)
   добива **ID token** со `nonce` што клиентот го генерирал и го праќа на `POST /v1/auth/{google|apple}`.
   API проверува: потпис (JWKS на провајдерот), `iss`, `aud` (нашите client ID-а), рок, `nonce`
   (Apple: SHA-256 од nonce). Е-поштата се зема само ако е `email_verified`.
2. **Email magic link** — `POST /v1/auth/email/start` праќа линк за една употреба (15 мин). Одговорот е
   секогаш ист (`202`), без разлика дали сметката постои или е достигнат лимитот (5 линка/час по адреса).
   Токенот е во фрагментот на URL-то (`#token=`) — не стигнува до серверски логови.
   Web страницата го праќа на `POST /v1/auth/email/verify`.

### Поврзување сметки

- Сметката се наоѓа по (провајдер, `sub`). **Google/Apple никогаш не се спојуваат автоматски** со постојна
  сметка по е-пошта → `409 account_exists` со листа на постојни методи; корисникот се најавува со постојниот
  метод и го поврзува новиот во профилот (`/v1/me/identities/...`).
- **Email** линк се поврзува со постојна сметка со иста адреса — контролата врз сандачето е веќе каналот за
  враќање на сметка.
- Последниот метод за најава не може да се отстрани.

### Токени и сесии

|         | Access token                                         | Refresh token                                                   |
| ------- | ---------------------------------------------------- | --------------------------------------------------------------- |
| Формат  | JWT, Ed25519 (`EdDSA`), `typ: at+jwt`, `sub` + `sid` | 256-битна случајна вредност, во базата само SHA-256             |
| Траење  | 15 мин                                               | 30 дена (лизгачки), сесија најмногу 180 дена                    |
| Web     | Во меморија на апликацијата                          | **HttpOnly, Secure, SameSite=Strict** колаче, патека `/v1/auth` |
| Мобилно | Во меморија                                          | Во OS keychain (`client: "native"` → во телото на одговорот)    |

- **Ротација** при секое освежување; повторно користење на веќе искористен токен (по 30 s толеранција за
  паралелни табови) ја **поништува целата сесија** (детекција на кражба, RFC 9700).
- Секое барање проверува дали сесијата е активна и ги чита улогите од базата → одјавата и промената на улога
  важат веднаш (цена: две мали прашања по барање; кеш подоцна ако треба).
- Освежување/одјава преку колаче бара заглавие `X-Requested-With: activen` (CSRF одбрана).
- Јавниот клуч е на `/.well-known/jwks.json` (идни сервиси, на пр. worker, можат сами да проверуваат).
- Во production `AUTH_SIGNING_KEY` е задолжителен (процесот не стартува без него); локално се генерира.

### Авторизација

- Глобален guard: секоја рута бара токен, освен означените со `@Public()`; `@Roles("coach")` за улоги.
- Улоги `athlete` и `coach` корисникот сам ги вклучува/исклучува (`PUT/DELETE /v1/me/roles/:role`);
  `admin` само оператор. Мора да остане барем една улога; тренер со активни спортисти прво ги завршува врските.

### Заштита и приватност

- Rate limiting: 20 барања/мин по IP на `/v1/auth/*`, 300/мин општо.
- Логовите ги редактираат `Authorization`, `Cookie`, `Set-Cookie`; во production email содржината (линкот) не се логира.
- Бришење сметка (`DELETE /v1/me`, потврда `"DELETE"`) ги брише сите податоци каскадно, веднаш (GDPR чл. 17);
  аудит записите остануваат без референца кон корисникот.

## Последици

- - Една шема и еден модел на корисник; сè е покриено со интеграциски тестови (вклучително вистински потпишани
    ID токени со тест-клучеви).
- - Нема трошок по корисник ни зависност од надворешен IdP.
- − MFA/passkeys не се дел од овој инкремент (Google/Apple веќе имаат своја MFA; passkeys — подоцна).
- − Потребни се Google OAuth client ID и Apple Developer сметка за вистинска најава; email провајдер
  (ЕУ, на пр. Amazon SES Frankfurt / Postmark) се додава со deploy инкрементот — дотогаш линкот е во логот.
