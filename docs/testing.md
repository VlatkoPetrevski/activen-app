# Тестирање

Секој инкремент мора да помине `pnpm verify` (format → lint → build → typecheck → test со праг на
покриеност). Тестовите се во четири слоја: од најбрзите и најбројните до најреалистичните.

| Слој            | Каде                                                                    | Што проверува                                                                    | База                 |
| --------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------- | -------------------- |
| Unit            | `packages/domain/test`, `packages/i18n/test`, `packages/contracts/test` | чисти правила: спојување на извори, зони, парсер на тренинзи, аналитика, формати | —                    |
| Repository      | `packages/db/test`                                                      | SQL, ограничувања, трансакции, миграции                                          | вистински PostgreSQL |
| API интеграција | `apps/api/test`                                                         | HTTP → контролер → сервис → база: авторизација, согласности, валидација, грешки  | вистински PostgreSQL |
| Web             | `apps/web/test`                                                         | компоненти и цели корисничко патувања врз демо API-то                            | —                    |
| Реален стек     | `tools/qa`                                                              | Playwright: web + API + база заедно; axe WCAG 2.1 AA на сите екрани              | вистински PostgreSQL |

## Покриеност (минимални прагови)

| Пакет     | Линии | Гранки | Моментално                 |
| --------- | ----- | ------ | -------------------------- |
| domain    | 90%   | —      | 99.9% линии                |
| contracts | 90%   | 80%    | 98.6% линии                |
| db        | 90%   | 80%    | 97.1% линии                |
| api       | 90%   | 80%    | 99.6% линии · 91.7% гранки |
| web       | 90%   | 75%    | 95.9% линии · 80.8% гранки |

Праговите се во `vitest.config.ts` / `vite.config.ts` на секој пакет. Кога покриеноста расте, прагот се
крева, никогаш не се спушта.

## Интеграциски тестови на API-то

Тестовите креираат привремена база на серверот од `TEST_DATABASE_URL` (стандардно локален Postgres),
ги пуштаат миграциите и ја бришат базата на крај (`packages/db/test/global-setup.ts`).

```bash
TEST_DATABASE_URL=postgres://postgres:postgres@localhost:5432/postgres pnpm --filter @activen/api test
```

`apps/api/test/harness.ts` е заедничката основа:

- `startHarness()`: вистинска Nest апликација со мејлер што ги фаќа магичните линкови;
- `signIn(h)` / `signInCoach(h)`: најава преку вистинскиот email тек, со случајна адреса;
- `link(h, coach, athlete, scopes)`: покана и прифаќање со дадени согласности;
- `addActivity(h, userId, date, overrides)`, `planBody(date, overrides)`.

Секој тест си прави свои корисници, па тестовите не зависат еден од друг и не мора да се чисти база.

### Сценарија што се покриени

- **`access.test.ts`**: матрица на авторизација. Секоја тренерска рута се пробува без токен (401), без
  улога тренер (403), како тренер без врска, со неприфатена покана и по прекината соработка (404).
  ID од туѓи податоци одговараат исто како непостоечки (без „пробување“). Се проверува и
  повторна покана по прекин.
- **`consent.test.ts`**: секоја комбинација од согласности на секое тренерско читање: календар,
  активност, напредок, аналитика, листа и одговор на активност. Strava податоците никогаш не стигнуваат
  до тренер. Промена на согласност важи од следното барање, а прекинот веднаш го одзема пристапот.
- **`plan-lifecycle.test.ts`**: истовремени измени од спортист и тренер (верзија → 409), структурирани
  тренинзи, валидација на рабовите (422 + problem+json), повеќе тренинзи во ден, check-in, пораки.
- **`web-contract.test.ts`**: секое барање што го прави web клиентот (`HttpApi`) мора да постои во OpenAPI
  документот на серверот. Ако се преименува или отстрани endpoint, тестот паѓа тука, не во продукција.
- `auth.test.ts`, `training.test.ts`, `workouts.test.ts`, `api.test.ts`: најава, сесии, профил, тренинг,
  структурирање на тренинзи и конфигурација.

## Web тестови

`apps/web/test/support/app.tsx` ја рендерира целата апликација врз `DemoApi` (`start()`, `asAthlete()`,
`asCoach()`, `nav()`). Патувањата се во `test/journeys/` по функционалност: `athlete`, `coach`, `plan`,
`profile`, `share`, `workouts`. Тестовите ја користат апликацијата како корисник: по улога и видливо
име (`getByRole("button", { name: "Зачувај" })`), никогаш по CSS класа. Така истите тестови
проверуваат и пристапност.

Правила што ги чуваат тестовите:

- корисникот секогаш добива локализирана порака, никогаш англиски текст од серверот
  (`errorMessageKey` во `ui/States.tsx`);
- поставките се оптимистички: промената се гледа веднаш и се враќа ако зачувувањето не успее;
- демото ги применува истите правила за согласност како серверот (`Viewer` од `@activen/contracts`).

## Договор помеѓу пакетите

- `packages/contracts/test/workout-contract.test.ts`: секој предлог од парсерот мора да помине
  шемата за зачувување на API-то.
- `@activen/contracts` (`viewer.ts`): серверот и демото ги делат правилата за тоа што гледа тренерот.
- `HttpApi` и `DemoApi` го имплементираат истиот `Api` интерфејс, што го проверува TypeScript.
